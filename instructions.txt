# 7. QR-CODE INVITATIONS AND SECURE CHECK-IN

QR invitations are a critical security-sensitive feature.

## 7.1 Invitation Tokens

Generate a unique, unpredictable token for every invitation or independently verifiable invitation entitlement.

Use cryptographically secure random generation.

Do not encode sequential database IDs, telephone numbers, email addresses, financial data, or other sensitive personal information directly into QR codes.

The QR code should contain an opaque verification URL or token that the server can validate.

Where practical, store a cryptographic hash of the verification token and compare it securely during verification.

Tokens must support revocation and replacement.

If an invitation is revoked or replaced, the previous token must no longer authorize entry.

## 7.2 QR Scanning

Build a mobile-first scanner interface for authorized entrance attendants.

The scanner must support:

* Camera-based QR scanning on compatible devices.
* Permission-denied handling.
* Camera-unavailable handling.
* Invalid QR codes.
* Revoked invitations.
* Invitations belonging to another event.
* Already-checked-in invitations.
* Valid invitations.
* Manual lookup when authorized.
* Clear, readable status messages.
* Controlled camera startup and shutdown.

Use HTTPS and browser permission requirements correctly.

Do not assume every browser or device supports camera scanning.

Provide a reasonable manual verification fallback.

## 7.3 Duplicate Check-In Prevention

The server must be the authority for check-in decisions.

A successful scan must record:

* Invitation identifier.
* Event identifier.
* Authorized attendant.
* Check-in timestamp.
* Verification outcome.
* Any required audit metadata.

Prevent concurrent requests from checking in the same entitlement twice.

Use appropriate database transactions, uniqueness constraints, row locking, or equivalent concurrency-safe mechanisms.

A browser-side check alone is insufficient.

Repeated scans must produce an explicit already-used response without creating duplicate successful attendance records.

## 7.4 Family and Group Invitations

Support invitation configurations for:

* One named guest.
* A guest plus an allowed number of companions.
* A family or group invitation.
* Separate individual entitlements when independent check-in is required.

The system must clearly distinguish between an invitation, the people it covers, and individual attendance records.

Do not allow guests to increase their permitted attendance count by modifying browser requests.

## 7.5 Offline Operation

The initial release may use online verification only.

Do not silently implement insecure offline acceptance.

If offline scanning is later authorized, design it as a separate phase with explicit synchronization rules, signed verification data where appropriate, device authorization, conflict resolution, and clear limitations.

Do not claim that offline verification can guarantee globally unique entry when multiple disconnected scanners cannot communicate.

# 25. FINAL ACCEPTANCE CRITERIA

The platform will not be considered production-ready merely because all pages load.

The applicable release criteria include:

* Organizers can securely create and manage multiple events.
* Event data remains isolated between unauthorized users.
* Invitation templates produce usable, correctly rendered cards.
* Invitations can be shared and opened securely.
* QR tokens are unpredictable, revocable, and validated on the server.
* Unauthorized and revoked invitations are rejected.
* Duplicate successful check-ins are prevented.
* Guests can submit RSVPs according to event rules.
* Financial totals distinguish pledges, received contributions, and expenses.
* Financial changes are auditable.
* Role and event permissions are enforced server-side.
* The interface works on supported mobile and desktop layouts.
* English and Swahili interfaces function correctly.
* Automated tests cover the critical workflows.
* External integrations are verified or clearly marked as unavailable.
* Production configuration does not expose secrets.
* Backup restoration and deployment procedures have been tested before launch.
* Remaining limitations and risks are documented honestly.

Not every acceptance criterion must be completed in Phase 0. Each subsequent phase must satisfy its own agreed acceptance criteria before moving forward.
